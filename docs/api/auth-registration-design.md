## API 계약 초안

공통 응답 필드는 팀 규칙을 따르고, 아래 data 구조와 HTTP 상태는 제안으로 검토한다.

### AU-03 회원가입

| 항목           | 내용                                       | 상태                    |
| -------------- | ------------------------------------------ | ----------------------- |
| Method·경로    | POST /api/v1/auth/register                 | 기존 API 초안           |
| 이용 대상      | 비회원의 고객 계정 가입                    | 기존 API 초안           |
| 요청           | email, password, agreements                | 사용자 화면 반영 설계안 |
| 정상 응답      | HTTP 201, data에 userId/email              | 제안                    |
| 계정 생성 정책 | 서버에서 role=CUSTOMER, status=ACTIVE 지정 | 제안                    |
| 화면 흐름      | 가입 완료 안내 후 로그인 화면으로 이동     | 프론트 협의 대기        |

#### 요청 필드와 저장 대응

| 필드       | 용도                            | 저장·처리                                       | 미정 항목                               |
| ---------- | ------------------------------- | ----------------------------------------------- | --------------------------------------- |
| email      | 로그인 아이디                   | users.email, DB UNIQUE 및 중복 확인             | 이메일 비교·길이·형식 검증 기준         |
| password   | 로그인에 사용할 비밀번호        | 비밀번호 전용 해시를 users.password_hash에 저장 | 길이·허용 문자, 프론트 연동 규격        |
| agreements | 약관 종류·버전·동의 여부의 목록 | user_agreements                                 | 필수 동의 항목·허용 버전·중복 입력 처리 |

agreements의 각 항목은 type/version/agreed 필드로 구성하는 방안을 제안한다.
기존 ERD의 TERMS·PRIVACY를 사용하며, 필수 동의 여부와 실제 약관 버전은 프론트 담당자와 맞춘다.
서버에서 허용하는 약관 종류·버전과 동의값을 검증하고 동의 시각을 기록한다.

요청 바인딩은 합의된 필드로 제한한다.
계정 역할·상태의 지정 권한은 서버에 두며, 추가 필드에 대한 오류 처리 방식은 계약 확정 시 기록한다.
응답에는 회원 식별 정보와 화면 처리에 필요한 데이터만 포함한다.

### AU-04 이메일 중복 확인

| 항목        | 내용                                | 상태          |
| ----------- | ----------------------------------- | ------------- |
| Method·경로 | GET /api/v1/auth/email-availability | 기존 API 초안 |
| 요청        | query parameter email               | 제안          |
| 정상 응답   | HTTP 200, data에 email/available    | 제안          |
| 입력 오류   | HTTP 400과 합의한 errorCode         | 제안          |

가입·중복 확인·로그인·계정 복구에 같은 이메일 비교 정책을 적용하도록 설계한다.
화면에서 중복 확인이 성공한 뒤에도 회원가입 시점에 서버에서 다시 검사한다.
가입 가능 여부 공개 범위와 호출 제한은 이 기존 API의 상세 계약을 협의할 때 확인한다.

### AU-01 로그인과 상태 유지

| 항목              | 내용                                                               | 상태                             |
| ----------------- | ------------------------------------------------------------------ | -------------------------------- |
| Method·경로       | POST /api/v1/auth/login                                            | 기존 API 초안                    |
| 요청              | email, password, rememberMe                                        | 화면 기반 요청안, 상세 계약 협의 |
| rememberMe 기본값 | false                                                              | 제안                             |
| 계정 판단         | 비밀번호 일치와 ACTIVE 계정 확인, CUSTOMER·STORE_ADMIN의 역할 활용 | 제안                             |
| 정상 응답         | HTTP 200, 토큰과 필요한 회원 정보                                  | 제안, 상세 필드·전달 경로 협의   |
| 페이지 성공 처리  | 프론트에서 홈 또는 검증된 내부 복귀 경로로 이동                    | 프론트 흐름 협의                 |
| 모달 성공 처리    | 모달을 닫고 현재 화면의 로그인 상태 갱신                           | 화면 기반 제안                   |

별도 페이지와 모달이 같은 로그인 API와 검증 기준을 사용한다.
서버는 선택한 비밀번호 전용 검증 함수로 저장 해시와 입력값의 일치를 확인한다.
로그인 응답으로 원래 비밀번호나 저장 해시가 전달되는 동작은 차단한다.

rememberMe는 로그인 상태 유지 의도를 전달하는 값이다.
쿠키 기반 Refresh Token 전달을 선택할 경우, 미선택은 비지속 쿠키, 선택은 만료 시각이 있는 지속 쿠키를 사용하는 방안을 검토한다.
쿠키의 HttpOnly·Secure·SameSite·CSRF 대응과 토큰의 서버 만료·폐기는 토큰 계약에서 함께 결정한다.
브라우저 세션 복원으로 세션 쿠키가 유지될 수 있으므로 브라우저 종료만으로 로그아웃을 보장하지 않는다.
Access Token·Refresh Token의 유효시간, 전달·저장 위치, 회전 정책은 기존 refresh_tokens 설계와 함께 합의 대기로 관리한다.

내부 예외·DB 접속 정보·비밀번호·해시는 응답 및 로그에서 보호한다.

## 회원가입 처리 설계

1. 합의된 필드·형식·길이와 약관 동의를 검사한다.
2. 합의한 이메일 비교 정책을 적용하고 중복 여부를 확인한다.
3. 선택한 비밀번호 전용 해시 함수로 비밀번호를 변환한다.
4. 하나의 트랜잭션에서 users와 user_agreements를 저장한다.
5. 커밋 후 회원가입 결과를 반환한다.

트랜잭션은 회원과 동의 저장을 함께 완료하거나 함께 취소하는 처리 단위다.
해시 계산과 저장 트랜잭션의 경계는 DB 연결 점유와 실패 처리를 고려해 구현 시 결정한다.

동시 가입은 users.email의 기존 UNIQUE 제약으로 최종 보호한다.
이메일 UNIQUE 위반만 이메일 중복 응답으로 처리하고, 다른 저장 오류는 해당 오류 정책으로 처리한다.
같은 이메일의 기존 계정 정보를 재가입 요청으로 덮어쓰는 동작은 차단한다.

## 기존 ERD 활용

| 기존 테이블     | 기존 항목                        | 이번 기능에서의 사용                                           |
| --------------- | -------------------------------- | -------------------------------------------------------------- |
| users           | id, email, password_hash         | 회원 식별·가입 정보                                            |
| users           | nickname                         | 기존 컬럼 활용. 가입 화면 외 정보이며 NULL 허용 저장 방안 제안 |
| users           | role, status                     | 계정 역할·이용 상태                                            |
| users           | name, phone                      | 기존 선택 정보, 후속 계정 정보·복구 기능에서 수집 범위 협의    |
| users           | created_at, updated_at           | 서버에서 관리하는 생성·수정 시각                               |
| user_agreements | id, user_id                      | 회원별 동의 이력의 식별자·외래 키                              |
| user_agreements | type, version, agreed, agreed_at | 약관 종류·버전·동의와 시각                                     |
| refresh_tokens  | 기존 ERD 정의                    | 토큰 기능 단계에서 사용                                        |

users와 user_agreements는 기존 ERD의 1:N 관계를 활용한다.
이메일 UNIQUE, 서비스별 독립 DB, 복수형 snake_case, Flyway 기반 변경 규칙을 적용한다.
컬럼 길이·NULL 허용·ID 생성 방식·인덱스·추가 제약은 마이그레이션 설계 시 기존 계약과 대조한다.
Auth DB 생성·접속 계정·공용 서버 설정이 필요한 경우 DB 담당자와 연결 정보를 맞춘다.

회원가입에서 요구하는 입력은 제공된 화면을 따른다. nickname·name·phone의 저장 제약은 기존 ERD 상세화 때 확인한다. 역할·상태는 서버가 관리하고 공개 가입 입력으로 관리자 권한이 생성되는 동작을 차단한다.

가입 시 users와 user_agreements를 같은 트랜잭션으로 저장하고 DB UNIQUE로 동시 중복 가입을 보호하는 기존 설계를 따른다. 이메일 중복 확인 결과와 별도로 가입 시점의 중복 여부를 검사한다. 이메일 소유 확인은 기존 결정대로 후속 제안 항목이다.

### 프론트 담당자와 확인할 최소 항목

1. 이메일 비교·형식과 비밀번호 길이·허용 문자 기준

4. 로그인 rememberMe와 Access/Refresh Token 전달·보관·만료 방식, 로그인 성공 시 페이지·모달 처리

비밀번호 해시 알고리즘은 Auth 내부 선정 항목으로 관리한다. 새 라이브러리의 채택은 CLAUDE.md의 사전 승인 규칙을 적용한다. 후보값의 확정은 이 문서의 결정 기록에 남긴다.

## Issue #94 구현 준비

2026-11-18 [Auth 회원가입·이메일 중복 확인 Issue #94](https://github.com/ktcloud-cloudnative-2026/team02-5xx/issues/94)를 생성했다. 작업 브랜치는 `feat/94-auth-registration`이다.

첫 구현 범위는 AU-03 회원가입과 AU-04 이메일 중복 확인, 기존 users·user_agreements의 저장 및 관련 검증이다. 상세 요청·응답, 입력 제한, 약관 버전과 해시 의존성은 위 표의 제안·협의 상태를 기준으로 상세화한다. 이 문서를 작업 브랜치에 복사한 시점에 미정값을 확정한 것으로 간주하지 않는다.

## 2026-11-18 Issue #94 로컬 구현 기록

- 사용자는 Issue #94의 회원가입·이메일 중복 확인 구현과 로컬 검증을 지시했다.
- JPA·Flyway·PostgreSQL 드라이버·입력 검증 및 Argon2id를 위한 Spring Security Crypto 7.1.2·BouncyCastle 1.87 도입을 승인했다.
- API·화면 연결의 실행 가능한 개발 계약은 services/auth-service/README.md에 기록한다. 길이 12~64자, 이메일 비교, 요청·응답·오류 코드, CUSTOMER·ACTIVE 및 선택 정보 NULL은 개발 구현 선택이며 프론트·DB 상세 계약 확인 대상이다.
- 실제 약관 버전의 기본값은 빈 값이다. 로컬 테스트만 local-test-v1을 사용한다. 실제 버전이 준비되지 않은 회원가입은 503으로 처리한다.
- 기존 Method·URL·ERD 테이블과 공통 응답 형식을 사용한다. 로그인·JWT·Refresh Token은 후속 기능으로 관리한다.
