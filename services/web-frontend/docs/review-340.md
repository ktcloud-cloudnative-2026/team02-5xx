기준: `feat/304-admin-layout-routing`, `2ea466562110784bf0c65b069ebe4c744070f51f`.
[리뷰](https://github.com/ktcloud-cloudnative-2026/team02-5xx/pull/340#pullrequestreview-6052390541)의 필수 로그아웃 재시도 및 관리자 메뉴 권한 오류 처리만 보완한다.
#331 / `2cca05b`는 미병합이며 코드를 가져오지 않았다. 다른 서비스·Gateway·배포 설정은 변경하지 않는다.

## 로그아웃 재시도

`logoutRecovery.js`는 Application의 UI 상태를 관리하고 기존 AuthSession.logout/login에 위임한다.
로그아웃은 기존 계약대로 서버 응답 전에 로컬 인증을 제거한다. 보호 트리의 해제와 #home 복귀는 기존 최상위 역할 경계를 유지한다.

- 실패하면 공통 홈에 서버 완료를 확인하지 못했다는 안내와 **로그아웃 다시 시도** 버튼을 제공한다.
- 재시도 실패는 안내를 유지하고, 성공은 안내와 버튼을 제거한다. UI pending 상태와 single-flight로 중복 클릭을 막는다.
- 로그인 성공·새 검증 계정은 이전 오류를 폐기한다. 이전 실패 ID의 재시도는 실행하지 않는다.
- 진행 중 로그아웃/재시도가 끝나기 전에는 새로운 로그인 요청을 보내지 않는다. 늦은 결과도 새로운 계정의 오류 상태를 덮어쓰지 않는다.
- 기존 고객/관리자 보호 화면은 로컬 인증 해제로 unmount되며, 공통 홈의 안내는 Application 한 곳에서 표시한다. 고객 App·AuthSession·Auth API 코드는 변경하지 않았다.
- 데스크톱 사이드바와 모바일 고정 탐색이 새 재시도 버튼을 가리지 않도록 오류 영역에만 여백을 적용했다. 초기 브라우저 검사에서 발견한 버튼 가림은 수정 후 네이티브 클릭으로 재검증했다.

## 보안 확인: 실패 후 새로고침

**서버 로그아웃 실패를 서버 세션 종료로 간주하지 않는다.** HTTP fixture에서 로그아웃 503이 Refresh 쿠키를 남기도록 설정한 뒤 CUSTOMER와 STORE_ADMIN 모두 다음을 실제 Chromium으로 확인했다.

1. 현재 문서에서는 로컬 인증과 보호 데이터가 제거되고 #home에 재시도가 표시된다.
2. 재시도 204 성공 뒤에는 쿠키가 제거되고 새로고침해도 비회원 홈을 유지한다.
3. 실패 상태 그대로 새로고침하면 새로운 AuthSession이 잔존 쿠키로 Refresh를 수행해 해당 역할의 인증이 다시 복원된다. 메모리 UI 오류 상태도 새 문서에 남지 않는다.

이는 현재 자동 복원 정책의 잔존 위험을 확인한 것이며 방지가 완료됐다는 뜻이 아니다. 오류 안내에도 새로고침 시 복원 가능성을 명시한다. 실제 Secure/Strict 쿠키·Gateway/dev E2E는 이 loopback 검증의 대상이 아니다.

추가 자동 복원 방지를 원한다면 별도 정책 선택이 필요하다.

- 탭별 sessionStorage에 자격 증명 없는 로그아웃 보류 표식을 두고 복원을 보류하는 방식: 같은 탭 새로고침을 막을 수 있지만 다른 탭에는 적용되지 않는다. 성공/로그인 때 표식 해제, 저장소 실패, 탭 종료, 계정 전환 및 사용자 복구 UX를 설계해야 한다.
- Auth 서비스의 세션 폐기 완료 확인과 실패 시 복구 흐름을 보강하는 방식: 서버 계약 및 출처/쿠키 보안 검토가 필요하다.

이번에는 AuthSession의 복원·토큰·Refresh 계약, 다른 탭의 계정으로 GET이 재시도될 수 있는 기존 동작을 임의로 변경하지 않았다.

## 관리자 메뉴 권한 경계

`adminMenuAccess.js`는 메뉴 페이지에만 적용되는 요청 세대·권한 경계다.
목록/상세/변경 요청의 401/403은 즉시 경계를 닫는다. 이전 목록·카테고리·선택 모달·성공 안내를 렌더링에서 제외하고 상태도 정리한다.
상세/등록/수정/상태 변경은 차단되며, 이미 열린 모달은 닫히고 오류 영역으로 포커스를 옮긴다.
권한 상실 전에 시작된 비동기 성공·실패는 이후 상태를 덮어쓰지 않는다. 이전 요청이 서버에 도달했을 수 있으므로 변경 요청을 자동 재전송하지 않는다.
새로운 정상 목록 조회에 성공하면 업무를 복구한다. 일반 네트워크·5xx 오류에서는 이전 목록을 유지한다.
403은 메뉴 경계만 닫으며 전역 세션 종료나 Refresh를 수행하지 않는다. 401의 세션 만료 처리는 기존 AuthSession과 최상위 경계를 그대로 따른다.

- 기존 PATCH 403 시나리오의 모달 유지 기대는 새 권한 정리 요구에 맞춰 모달/행 제거·등록 차단·정상 조회 복구로 변경했다. 원래의 요청 1회·Refresh 없음·세션 유지 검증은 보존했다. 테스트를 삭제하거나 조건을 약화하지 않았다.
- Vite Build, 제품 번들 경계, 전체 Prettier(Git LF 스냅샷), git diff --check 모두 PASS. 원래 Windows checkout의 전체 Prettier는 기존 CRLF 파일 158개에서 실패하여 Git LF 스냅샷으로 전체 검증했다. Windows checkout의 기존 CRLF는 unrelated 전체 파일 포맷 변경으로 해결하지 않는다.
- 이 브랜치의 요청된 회귀에서 잔여 실패는 없다. #331 별도 브랜치의 기존 실패나 수정 코드는 가져오지 않았다.

- 하단 **로그아웃 응답**을 `실패 503 (쿠키 유지)`로 두고 로그인 후 로그아웃한다. 공통 홈의 재시도 실패/유지를 확인한 다음 하단 응답을 `정상 204`로 바꾸고 재시도하면 안내가 사라진다.
- 실패한 상태로 새로고침하면 위에 기록한 기존 쿠키 복원 동작을 확인할 수 있다.
- 관리자로 로그인해 메뉴 목록을 조회한 뒤 하단 **메뉴 목록 응답**을 `권한 오류 403`으로 바꾸고 목록을 새로고침한다. 행과 등록 접근이 사라진다. `정상 200`으로 바꾸고 다시 불러오면 복구된다.
- **메뉴 저장 응답**을 `권한 오류 403`으로 설정한 뒤 수정 모달에서 저장하면 모달과 보호 데이터가 정리된다. 정상으로 바꾼 뒤 목록을 다시 불러와 복구한다.
- 개별 응답 선택기는 인증/데이터 초기화 없이 동작한다. 전체 **통합 시나리오** 변경은 기존대로 검수 데이터와 인증을 초기화한다.
