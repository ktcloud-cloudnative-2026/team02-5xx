# Menu Service dev 테스트 데이터 시드

관련 Issue: #217. **dev 전용, 수동 실행 전용**입니다. 이 디렉터리는 Flyway의 `db/migration` 경로 밖에 있습니다. 파일이 `main`에 병합돼도 SQL은 자동 실행되지 않습니다.

## 범위와 테스트 포인트

- 카테고리 4건: 버거, 사이드, 음료, 디저트
- 메뉴 12건: `ON_SALE` 8건, `PAUSED` 2건, `HIDDEN` 2건
- 옵션 20건: 활성/비활성, 기본 옵션, 추가 금액·조리 시간 0 및 양수 혼합
- `아이스 아메리카노`: 설명·이미지 NULL, 옵션 없음
- 이미지 URL은 모두 NULL입니다. 프론트엔드의 이미지 대체 UI를 검증하고, 외부 이미지 URL 의존성을 피합니다.
- 서로 다른 카테고리의 메뉴에 같은 가격(예: 3,500원)이 있어 가격 동률 정렬을 확인할 수 있습니다.
- 공개 API의 목록에는 HIDDEN 2건이 보이지 않으며, PAUSED 2건은 목록·상세 조회가 가능하되 구매 검증에는 실패해야 합니다.
- Inventory의 수량·품절 상태는 **별도 Inventory DB** 소유이며 이번 SQL에 포함하지 않습니다.

## 안전 장치

- SQL은 정확히 `menu_dev` DB에서만 실행됩니다. 다른 DB면 예외를 발생시킵니다.
- 세 테이블 중 **어느 하나라도 데이터가 있으면** 실행을 거절합니다. 기존 데이터를 삭제하거나 수정하지 않습니다.
- 테이블 잠금과 단일 트랜잭션으로 중간 실패 시 부분 삽입을 방지합니다.
- 성공 후 건수와 상태별 건수를 검증합니다. 예상과 다르면 트랜잭션을 롤백합니다.
- **재실행은 성공 처리하지 않고 명시적으로 거절**합니다(중복 삽입 방지).
- 비밀번호는 SQL과 Git에 넣지 않습니다. `-W` 프롬프트로 입력합니다.
- 운영 DB 또는 `prod`에서 실행하지 않습니다. 별도 초기 데이터 정책이 확정되기 전까지 운영 데이터로 재사용하지 않습니다.

## 적용 전 조건

1. Issue #217 대응 PR이 리뷰/CI를 통과하고 `main`에 병합되었는지 확인합니다.
2. `t2-db`에서 `menu_dev_user`로 접속할 권한이 있는지 확인합니다.
3. `flyway_schema_history`에서 V1 성공을 확인합니다.
4. `categories`, `menus`, `menu_options`의 건수가 모두 0인지 재확인합니다.
5. SQL 파일을 Windows PC에서 DB 서버로 안전하게 전송합니다. `t2-dev-cp`에는 설치하거나 부하 작업을 실행하지 않습니다.

**DB 서버(t2-db)의 Linux 셸에서** 다음처럼 실행합니다. 아래 경로는 SQL을 전송한 위치에 맞춰 수정할 수 있습니다.

```bash
psql -X -v ON_ERROR_STOP=1 \
  -h 127.0.0.1 -p 5432 \
  -U menu_dev_user -d menu_dev -W \
  -f /tmp/peakorder-menu-dev-seed.sql
```

예상 결과:
- `categories=4`, `menus=12`, `menu_options=20`
- `ON_SALE=8`, `PAUSED=2`, `HIDDEN=2`

## 적용 이후 검증

```bash
psql -h 127.0.0.1 -p 5432 -U menu_dev_user -d menu_dev -W \
  -c "SELECT status, count(*) FROM menus GROUP BY status ORDER BY status;"
```

Menu Service 실제 배포 후 `GET /api/v1/menus`의 메뉴 10건과 상세·옵션 조회, 내부 구매 검증(MI-01), 존재 확인(MI-02)을 별도로 검증합니다. 테스트 데이터는 실제 재고 상태나 주문 가능 여부를 보장하지 않습니다.

## 운영 및 복구

- 실행 실패 시 psql 연결이 종료되면 미커밋 트랜잭션은 롤백됩니다. `-v ON_ERROR_STOP=1`을 필수로 사용합니다.
- 이미 성공한 데이터의 자동 삭제·강제 초기화 스크립트는 제공하지 않습니다. DB에서 테스트 주문·재고 연결이 생긴 뒤 일괄 삭제하면 참조 관계를 손상시킬 수 있기 때문입니다.
- 데이터를 바꾸거나 삭제해야 하면 DB 담당자와 영향을 확인하고 **별도 Issue/PR**로 관리합니다.
